# Isolated PACT, Python, JavaScript and C counter adapters

The execution adapters target the frozen `counter-four` task for PACT, Python, JavaScript and C. They run the PACT reference interpreter, Python candidate code, a JavaScript ES module or a compiled C candidate in a disposable Docker container, produce the same external trace format and feed observations to the independent trace grader.

```sh
docker build -f benchmarks/sandbox/Dockerfile -t pact-counter-verifier .
docker image inspect --format '{{.Id}}' pact-counter-verifier
python3 -m benchmarks.agent_sandbox archived-candidate.pact --image sha256:IMAGE_ID_FROM_INSPECT
python3 -m benchmarks.agent_sandbox archived-candidate.py --language python --image sha256:IMAGE_ID_FROM_INSPECT
python3 -m benchmarks.agent_sandbox archived-candidate.mjs --language javascript --image sha256:IMAGE_ID_FROM_INSPECT
python3 -m benchmarks.agent_sandbox archived-candidate.c --language c --image sha256:IMAGE_ID_FROM_INSPECT
```

The image argument must be a complete immutable local image ID. Tags, registry references and automatic pulls are rejected. Building the trusted image can use the network; candidate execution cannot. The Dockerfile's base tags is not a reproducible-build lock: archive the resulting image and receipt's image ID to rerun that exact runtime. The image is an operator-trusted executable dependency, not candidate-controlled input.

## Execution boundary

Linux and an accessible Docker Engine are required. Missing backend, unsupported platform, mutable image identifier or weakened inspected configuration rejects; there is no host-execution fallback. The runner creates a named container, inspects its effective configuration, sends only the bounded candidate snapshot and frozen call arguments through stdin, runs the worker, and forcibly removes the container in a `finally` block. A cleanup failure prevents a success receipt.

Requested constraints are network `none`, read-only root filesystem, UID/GID 65534, all capabilities dropped, no-new-privileges, 128 MiB memory with no extra swap, one CPU, 32 processes, CPU/file/descriptor limits and a 16 MiB temporary filesystem. No host mounts, Docker socket, credentials or host environment variables are passed into the container. Automatic image volumes reject. The worker stages candidate data in its bounded temporary filesystem. The worker is fixed inside the trusted image; candidate source is never a shell command. PACT source is interpreted as closed-schema IR; Python source is compiled/executed and JavaScript source is imported only inside the container, with no host execution fallback. It accepts exported `advance(index, amount) -> unit` and a two-element counter. Reference evaluation has a 100,000-node budget for the sequential calls and a fresh budget for the reset observation.

Each candidate read is bounded to 1 MiB. Worker execution has a 15-second wall-clock limit; Docker control operations have separate 10-second timeouts. Trusted worker JSON and diagnostics are small, but Python/JavaScript/C candidates may emit arbitrary output or alter in-process worker state. A streaming capture shares a 1 MiB budget across stdout/stderr, kills the Docker CLI when exceeded and then forcibly removes the container. Stored log bytes never exceed that cap; reader chunks and bounded stdin are additional transient allocations. Timeout/runtime failure observations retain raw captured output in the receipt. Infrastructure errors reject rather than inventing a successful execution.

Docker's configured restrictions depend on the host kernel and daemon. This adapter is not a VM, independent bytecode verifier, authenticated evaluator or proof against kernel/container escapes. Configuration inspection and finite CI fixtures do not establish universal containment. Use a disposable worker host without credentials for model trials. The [Docker run reference](https://docs.docker.com/engine/containers/run/) documents the requested resource and privilege controls; candidate bytes are transferred through the attached stdin stream.


## C execution details

GCC compiles C11 with `-O2 -Wall -Wextra -Werror`, linking the candidate and trusted driver as separate translation units. Compiler diagnostics stream into the existing outer stderr capture; the compiler subprocess has a 10-second timeout within the overall 15-second execution limit. A compiler failure produces a `compile_error` observation with GCC version metadata and no invented cases. Missing toolchains/backend errors fail closed. The runtime image ID pins the actual compiler, headers and libraries; mutable Docker base tags and package repositories do not provide a reproducible-build lock.

The candidate source, generated driver and compiler output are staged under the bounded `/tmp`. Its `noexec` mount option remains set. The worker copies at most 1 MiB of compiled bytes into a Linux `memfd` and replaces itself with that executable through its descriptor. The native driver runs the ordered calls, then forks and re-executes the same descriptor for the isolated reset observation, so static variables and initializers start fresh. This intentionally permits native execution inside the container: `noexec` on `/tmp` is not a claim that anonymous executable memory or arbitrary native code is forbidden. The effective container restrictions and outer output/time limits apply to compilation and native processes. GCC version observations are unauthenticated, as are Node/V8 observations. Native code may corrupt its own driver, read the container image or forge output; the independent host-side exact-source policy does not authenticate execution.

## Receipts and scope

`pact.agent-sandbox-receipt/0.6` contains the immutable image ID, generated external trace, grader report, restricted source-policy report and raw stdout/stderr encoded as base64. Version 0.6 adds separate PACT `embedded_tests` observations and requires their successful execution for CLI success. Historical receipts retain their original scope. Version 0.5 added C selection and GCC metadata in `runtime`. Version 0.4 added JavaScript selection and a separate `runtime` observation with Node/V8 versions (null when unavailable or for PACT/Python). It is unauthenticated metadata; the immutable image ID identifies the trusted runtime snapshot. Version 0.3 added Python selection and explicit timeout/output-limit termination fields. Version 0.2 added source-policy requirements to CLI success; historical receipts are not reclassified automatically. Executor `log_sha256` hashes compact sorted-key JSON of that two-field log object. Source bytes are hashed before copying. The receipt reports that isolation configuration was checked, while `candidate_pass` remains null and `model_trial` remains false. The embedded grade also retains `execution_authenticated: false`; image and log identities are not signatures.

Exit 0 means the observed trace and restricted counter-four source policy match, and for PACT the declared tests also pass on actual WebAssembly; exit 2 means a behavioral or source-policy failure and exit 1 means invalid input or infrastructure rejection. Receipts include a separate static `policy` report. PACT permits only the frozen counter IR with repeat count 4 and the independent expected test value. Python permits only the frozen AST with `range(4)` instead of `range(3)`, ignoring source positions/comments/formatting; extra imports, statements or interface changes reject. JavaScript permits only the exact frozen source with `i < 4` instead of `i < 3`, normalizing CRLF to LF. It rejects other whitespace/comment changes as well as semantic changes. This deliberately conservative byte policy uses no host JavaScript parser or execution, and is stricter than the PACT IR and Python AST policies. C uses the same exact-source rule for its frozen `i < 3` → `i < 4` edit, also allowing only CRLF normalization. All four can reject behaviorally correct alternative rewrites. Compact/JSON formatting can differ without changing IR. The policy can reject other correct rewrites, does not measure textual diff size and is not a general source-policy verifier. Candidate functions are not run by the policy checker. PACT uses the reference interpreter for the external trace and separately compiles the same candidate and executes its declared tests on actual Wasm inside the same Docker boundary; Python uses CPython and JavaScript uses Node 24 inside the trusted image. The worker replaces its Python process with Node, so the outer capture/timeout applies directly. JavaScript reset imports a distinct module URL to re-evaluate top-level state; global process state is not erased and must not leak between observations. Runtime and source-policy asymmetries must be reported rather than presented as equivalent safety guarantees. No provider is called and no benchmark leaderboard is produced. Calling real models additionally needs an accessible provider endpoint/client, securely configured credentials, pinned settings and archived provider responses/usage. This runner alone does not supply that access.

The dedicated CI workflow builds the image, exercises authored baseline/edited/malformed fixtures and a behaviorally matching candidate rejected by the source policy in actual containers and archives their receipts. These are integration fixtures, not model results. Local environments without Docker can verify configuration and fail-closed behavior but cannot claim executed isolation. CI also exercises Python baseline/edited/invalid/noisy candidates, an output flood and wall-clock timeout, and archives receipts. JavaScript CI also covers baseline/edited/invalid/noisy candidates, an unapproved comment, an exact 1 MiB candidate, reset leakage, output flood and timeout; Node/V8 observations are archived. C CI covers baseline/edited/invalid source, an unapproved comment, a 1 MiB candidate, a fresh-process reset probe, noisy output, output flood, timeout and a native crash. Python, JavaScript and C code share a process and UID with their respective in-container drivers, so a malicious candidate may forge observations; the source policies are checked independently on the host, but receipts still do not authenticate execution or approve full candidate correctness. Broader adversarial containment probes, broader policies and real provider trials remain pending.


## PACT declared tests (receipt 0.6)

After collecting the external counter trace, the PACT worker calls the existing `build_module` pipeline inside Docker. It compiles the candidate to WebAssembly and runs every declared case through the trusted Node test host, with a fresh instance for each case. Declared initial-state overrides, arguments, expected state and optional numeric result are checked by the existing compiler/test schema. This does not change language semantics. The compiled bytes never execute on the outer host.

`embedded_tests` remains separate from the external trace and static policy:

| Status | `pass` | Meaning |
| --- | --- | --- |
| `passed` | true | All declared cases ran successfully on Wasm; `executed` equals the positive `declared` count |
| `failed` | false | Build/test execution rejected; `reason` retains its diagnostic code and bounded diagnostics remain in stderr; `executed` is null because the host may stop at its first failing case |
| `missing` | false | A legacy candidate declared no tests; zero cases is not a successful test execution |
| `not_run` | null | Parsing, external execution, timeout or infrastructure prevented a completed observation |
| `not_applicable` | null | Python/JavaScript/C task inputs have no embedded declaration interface; no test pass is invented for them |

The existing outer 15-second execution timeout, Docker CPU/memory/process/filesystem limits and output cap still apply to the whole candidate run, including compilation and Node tests. Before declaration execution, the worker flushes a framed reference checkpoint. The host validates its shape and, on a completed run, requires it to match the final trace. Timeout/resource termination during declarations retains this checkpoint for independent behavior grading while reporting tests as not-run and preventing CLI success. A dedicated authored fault-injection image stalls the trusted Node test host to exercise this boundary in Docker. Test failure does not erase a successfully collected external behavior trace. A failed external run cannot produce CLI success. Tests can be weak or incomplete; passing declarations is not adequate-coverage evidence, authenticated execution or full candidate correctness. `candidate_pass` remains null.

Authored Docker fixtures include valid declarations, a wrong expected value, an empty legacy test list and a declared out-of-bounds call. The latter three retain their behaviorally correct counter traces but fail declaration execution. Python/JavaScript/C remain explicitly asymmetric. Broader pre-registered policies and adversarial containment evidence remain unfinished E2/E3 work. Frozen model artifacts and historical results are not rewritten.
